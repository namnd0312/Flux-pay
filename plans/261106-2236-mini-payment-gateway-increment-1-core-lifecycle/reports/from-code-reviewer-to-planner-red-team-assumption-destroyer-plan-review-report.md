## Finding 1: Phase 4 webhook `process()` transaction design cannot deliver "always 200" — duplicate and late webhooks will 500
- **Severity:** Critical
- **Location:** Phase 4, "Architecture" + "Processing order" — `phase-04-sync-webhook-and-deduplication.md:26`, `:36-40`, invariant at `:20`
- **Flaw:** Line 26 declares `WebhookIngestionService  @Transactional process(providerCode, rawBody, headers)`. Line 36 then says step 1 runs "outside tx", line 39 says "on `IllegalPaymentTransitionException` mark event REJECTED (do not roll back the insert)", line 40 says "catch `DataIntegrityViolationException` on the insert ... -> 200 duplicate:true". None of that works inside one `@Transactional` method: (a) `stateMachine.transition()` is invoked through `PaymentOrchestrator`/repositories that join the outer tx; a RuntimeException escaping a joined `@Transactional` boundary marks the tx rollback-only, so the catch in `process()` is followed by `UnexpectedRollbackException` at commit — the REJECTED event row is lost and the provider gets 500. (b) On PostgreSQL a unique-violation aborts the transaction (`current transaction is aborted`); with JPA the violation surfaces at flush/commit, not at `save()`, so the `catch (DataIntegrityViolationException)` around "the insert" never fires where the plan puts it.
- **Failure scenario:** `mock.callback.duplicates=1` (the phase's own demo). First webhook APPLIED. Second webhook: exists-check passes (fast path) or loses the race; insert violates `(provider_code, event_id)`; tx aborted; Spring throws on commit; `ProblemDetailsHandler` returns 500; mock-provider retries 3x (line 17) — exactly the behaviour the phase claims to eliminate. Same for the late-webhook-after-EXPIRED demo: transition throws, catch "succeeds", commit throws, 500.
- **Evidence:** `phase-04:26` ("@Transactional process"), `:39` ("do not roll back the insert"), `:40` ("catch DataIntegrityViolationException on the insert"), invariant `:20` ("never returns 4xx/5xx for business rejections"). `WebhookIngestionIT` cases at `:47` ("duplicate -> no second transition", "webhook on EXPIRED -> REJECTED") are the ones that will fail.
- **Suggested fix:** Make `process()` non-transactional and use `TransactionTemplate` (or `REQUIRES_NEW` helper bean) per step: tx A = insert event (catch DIVE *outside* tx A -> duplicate); tx B = transition; on `IllegalPaymentTransitionException` caught *outside* tx B, tx C = update event to REJECTED. State explicitly that the transition call path must not share the event-insert transaction. Add `noRollbackFor` only if the plan keeps a single tx, and say so.

## Finding 4: Phase 3 "two-transaction create" via `PaymentOrchestrator` self-invocation silently collapses into no transaction or one transaction — the lesson cannot be observed or verified
- **Severity:** High
- **Location:** Phase 3 "Architecture" flow — `phase-03:39`; Phase 2 `phase-02:31` ("owns @Transactional boundaries"); Phase 3 Modify `:43` ("two-transaction create")
- **Flaw:** The flow is "insert CREATED (tx 1, commit) -> provider.createPayment() (outside tx) -> tx 2". With `PaymentOrchestrator` as the single `@Service` owning `@Transactional`, tx 1 and tx 2 are either private methods on the same bean (proxy bypassed on `this.` calls -> no transaction at all; `save()` auto-commits per repository call, which looks "fine" but is not what is taught) or `create()` itself is `@Transactional` (network call inside the tx — the anti-pattern the phase demonstrates). No step or success criterion asserts that a DB connection is *not* held during the provider call.
- **Failure scenario:** Failure demo step 1 (`:47`) and the "fixed" step 7 (`:53`) behave identically under observation; the user learns the slogan without the mechanism. Later, increment 2 "measures the bottleneck" (`:39`) against a baseline that was never real.
- **Evidence:** `phase-03:39` "Teach why the provider call must not sit inside a DB transaction"; `phase-02:31` "`PaymentOrchestrator (@Service) ... owns @Transactional boundaries`"; `phase-03:58-61` Success Criteria contain no transactional assertion.
- **Suggested fix:** Specify `TransactionTemplate` (or a separate `PaymentPersistence` bean) for tx 1 / tx 2 and add a test: provider stub asserts `TransactionSynchronizationManager.isActualTransactionActive() == false` and Hikari `active` == 0 during the call.

## Finding 6: Phase 6 burst tooling is undecided, one option is mathematically impossible, and the fallback deletes the failure demo
- **Severity:** High
- **Location:** Phase 6 "Related Code Files" `phase-06:40`, step 1 `:45`, Success `:58`, Risk `:66`; Phase 5 `:17`
- **Flaw:** `:40` offers three mutually exclusive signing approaches: "a tiny Java/Node helper or by reusing a pre-signed body with a fresh timestamp - simplest: `scripts/sign.sh` using `openssl dgst -sha256 -hmac`". "Pre-signed body with a fresh timestamp" is impossible because the timestamp is inside the signed payload (`phase-05:17`: `HMAC(secret, timestamp + "." + rawBody)`). The risk note `:66` then says "if too fiddly, fall back to a JUnit-driven burst only" — but step 1 (`:45`) and success criterion `:58` ("Burst demo recorded before (50 rows)") *require* the script to run against the phase 5 build, before `ConcurrentCreateIT` exists. The brainstorm decision for load tooling is JMeter (BR `:40`); a shell+openssl+xargs toolchain is new, undeclared tooling.
- **Failure scenario:** Implementer picks "fresh timestamp", every request 401s with `AUTH_BAD_SIGNATURE`, demo shows 0 rows instead of 50, note records the wrong failure.
- **Evidence:** `phase-06:40` quoted above; `:66` "keep `scripts/sign.sh` with `openssl`; if too fiddly, fall back to a JUnit-driven burst only".
- **Suggested fix:** Commit to one: sign once with a single timestamp (valid for 5 min) and replay the identical request 50x with `xargs -P` — no per-request signing needed — or ship the JMeter `.jmx` now (matches BR decision, user already knows JMeter per BR `:30`). Delete the "fresh timestamp" sentence and the JUnit-only fallback, or drop `:58`.

## Finding 9: Mock-provider webhook sender is specified as synchronous inside the pay request; delay/retry exercises block the caller and the sweeper IT has no time-control design
- **Severity:** Medium
- **Location:** `phase-04:17`, `:31`, `:62`; `phase-02:54`, `:35`
- **Flaw:** `phase-04:17` has `POST /mock/pay/...` "signs it, POSTs to ..." with `delay-ms`, `duplicates`, `retry-on-non-200 (default 3, with 1s backoff)`; `:31` lists `WebhookSender (RestClient, signing, delay, duplicates, retry)` with no executor/`@Async`. - **Failure scenario:** User follows `:62`, Postman appears frozen, user kills it; mock-provider never sends the webhook; "late webhook REJECTED" is never observed. Sweeper IT either sleeps 30 s+ or is flaky.
- **Evidence:** `phase-04:17`, `:31`, `:62`; `phase-02:35` "a `Clock` bean", `:54` "sweeper expires an overdue payment (use the `Clock` bean)".
- **Suggested fix:** Mark `WebhookSender.send` as `@Async` with a dedicated executor and return `202 {providerRef, status}` from pay immediately.
