## Finding 1: Unique (merchant_id, order_id) makes every FAILED/EXPIRED/CANCELLED order permanently unpayable, contradicting the plan's own retry semantics
- **Severity:** Critical
- **Location:** Phase 6, "Requirements" + "Architecture" — `phase-06-idempotency.md:22`, `:35`, `:50`; Phase 2 `phase-02-payment-state-machine.md:35`; Phase 3 `phase-03-provider-interface-and-mock-provider.md:19`
- **Flaw:** P6:35 says a provider 502 is a *completed* idempotent response and "the merchant must use a new key for a new attempt". P6:22/50 adds an unconditional unique `(merchant_id, order_id)` returning 409 `ORDER_ALREADY_EXISTS`. P2:35 makes FAILED/EXPIRED/CANCELLED terminal. The three together mean the "new attempt" is impossible: the terminal row occupies the unique slot forever.
- **Failure scenario:** (1) Merchant creates `ORD-1`, mock-provider is down (P3:55 Postman step) -> payment row FAILED, 502 stored against key K1. (2) Provider back; merchant follows P6:35, sends `ORD-1` with key K2 -> tx1 insert hits V7 unique -> 409 `ORDER_ALREADY_EXISTS`. (3) Same for a customer who let the payment EXPIRE (P2:20) or CANCELLED it and wants to pay again: the order is dead for 24h+ (forever; the unique is not TTL-bound). This is also the exact Postman path P6:54 ("new key same orderId (409)") — the plan tests the bug as if it were the feature.
- **Evidence:** P6:35 "the merchant must use a new key for a new attempt"; P6:22 "Duplicate `orderId` for the same merchant with a different key -> 409 `ORDER_ALREADY_EXISTS`"; P2:35 "terminal states -> none".
- **Suggested fix:** Make V7 a partial unique index `WHERE status IN ('CREATED','PENDING','SUCCEEDED')` (or exclude only FAILED/EXPIRED/CANCELLED) and state the rule explicitly in the note; or drop the order-level unique and rely on idempotency only (the brainstorm's "second guard" then needs a different definition). Either way P6:35 and P6:22 must be reconciled in text.

## Finding 2: `abandon()` cannot deliver the promised "client can retry" — any exception after tx1 orphans a CREATED row that blocks the retry
- **Severity:** High
- **Location:** Phase 6, "Architecture" — `phase-06-idempotency.md:35`, `:49`; Phase 3 "Flow" — `phase-03-provider-interface-and-mock-provider.md:39`, `:64`; Phase 2 `phase-02-payment-state-machine.md:20`, `:35`
- **Flaw:** The create flow commits CREATED in tx1 before the provider call (P3:39). If tx2 throws (DB blip, optimistic lock, mapping bug) or any non-`ProviderException` escapes, P6:35/49 deletes the idempotency key so the client can retry. The retry then does `begin()` -> NEW -> tx1 insert of the same `orderId` -> V7 unique -> 409. Additionally, nothing in increment 1 can ever move that CREATED row: the sweeper only touches PENDING (P2:20), CREATED has no `expires_at` semantics, and P3:64 explicitly punts CREATED cleanup to increment 4. Also, the tx2-failure branch is not specified at all: P3:53 only maps `ProviderException` -> FAILED; a tx2 failure after a *successful* provider session leaves CREATED + a live provider session + a 500 to the merchant.
- **Failure scenario:** Request A: tx1 commit CREATED(ORD-1) -> provider returns payUrl -> tx2 fails (e.g. connection reset). Controller catches, `abandon(K1)` deletes key, 500 returned. Merchant retries K1 -> NEW -> insert CREATED(ORD-1) -> DIVE -> 409 `ORDER_ALREADY_EXISTS`. Merchant retries with K2 -> same 409. Row stays CREATED forever; provider session is orphaned; no `queryStatus` (P3:30 throws `UnsupportedOperationException`).
- **Evidence:** P6:35 "`abandon()` (delete row) on unexpected exception so the client can retry"; P3:64 "leaves a CREATED row if the JVM dies between tx 1 and tx 2 -> acceptable here; increment 4 ... covers CREATED older than N minutes" (only JVM death is considered; tx2 exceptions are not).
- **Suggested fix:** On tx2 failure after a provider result, run a compensating tx: `transition(CREATED -> FAILED, reason=exception, SYSTEM)` (CREATED->FAILED is already allowed, P2:35) and store the 500/502 as a completed idempotent response rather than abandoning. Combine with Finding 1's partial index so FAILED frees the order slot. Extend the sweeper (P2:20) to also expire CREATED rows older than N minutes in increment 1 — it's one extra predicate, not increment-4 scope.

## Finding 3: Webhook `process()` catches constraint/transition exceptions inside one `@Transactional` method — in Spring+PostgreSQL this commits nothing and returns 500, triggering the mock-provider retry storm the phase is meant to eliminate
- **Severity:** High
- **Location:** Phase 4, "Architecture / Processing order" — `phase-04-sync-webhook-and-deduplication.md:26`, `:39`, `:40`; Requirements `:17`, `:20`
- **Flaw:** P4:26 makes `process()` a single `@Transactional`. P4:39 catches `IllegalPaymentTransitionException` *inside* it and says "do not roll back the insert"; P4:40 catches `DataIntegrityViolationException` on the event insert and returns 200 `duplicate:true`. Both patterns fail with the described wiring: (a) if `stateMachine.transition()` / the repository `save` is itself a `@Transactional` proxy (P2:31 says the orchestrator owns tx boundaries; `SimpleJpaRepository.save` is `@Transactional`), the inner proxy marks the shared tx rollback-only; the outer commit throws `UnexpectedRollbackException` -> 500 and the event row is lost. (b) A unique violation inside a PostgreSQL transaction aborts the whole tx ("current transaction is aborted"); nothing after the catch can be written, and the commit fails. (c) With JPA deferred flush, the insert's DIVE does not surface at the `save()` line at all but at commit time — outside the `catch` in step 5 — so it propagates as 500 regardless.
- **Failure scenario:** `mock.callback.duplicates=1` (P4:17). Two identical webhooks arrive within ms. Both pass the exists-check (P4:40 admits this). Second one: insert -> DIVE at flush/commit -> uncaught or tx aborted -> 500 -> mock-provider `retry-on-non-200` sends 3 more (P4:17) -> each 500 again (row now exists). Acceptance `plan.md:58` ("Duplicate webhook returns 200") fails under the exact config the phase ships. Same for the EXPIRED/CANCELLED late-webhook path (P4:19): the REJECTED marking is lost and the provider sees 500.
- **Evidence:** P4:26 "`WebhookIngestionService @Transactional process(...)`"; P4:39 "on `IllegalPaymentTransitionException` mark event REJECTED (do not roll back the insert)"; P4:40 "catch `DataIntegrityViolationException` on the insert ... -> 200 duplicate:true".
- **Suggested fix:** Split into explicit small transactions: `insertEvent()` in `REQUIRES_NEW` using a native `INSERT ... ON CONFLICT DO NOTHING RETURNING id` (same technique P6:33 already uses — reuse it), then `applyTransition()` in a second tx, then `markEvent(APPLIED|REJECTED)` in a third. Specify that `transition()` is not a tx proxy or is called with `noRollbackFor`. This also gives the raw-body-persisted-before-processing guarantee the increment-3 outbox lesson will need.

## Finding 4: Unknown-payment webhooks are stored before the dedup check and outside the constraint catch — a retried unknown event 500s
- **Severity:** Medium
- **Location:** Phase 4, "Processing order" — `phase-04-sync-webhook-and-deduplication.md:37`, `:38`, `:39-40`
- **Flaw:** Step 2 (P4:37) inserts a REJECTED `UNKNOWN_PAYMENT` event when the providerRef is not found; the dedup check is step 3 (P4:38) and the DIVE catch is step 5 (P4:40), scoped to the step-4 insert. The step-2 insert hits the same `(provider_code, event_id)` unique with no handler.
- **Failure scenario:** Hand-crafted webhook for a non-existent providerRef with `duplicates=1`, or a provider retry after a slow 200. First: stored REJECTED, 200. Second: step 2 insert -> unique violation -> 500 -> provider retries 3x -> 3 more 500s. The P4:20 invariant "never 4xx/5xx for business rejections" is broken on the first path the P4:52 failure demo exercises.
- **Evidence:** P4:37 "find payment by providerRef (404 -> store event REJECTED `UNKNOWN_PAYMENT`, 200)" precedes P4:38 "`existsByProviderCodeAndEventId` -> 200 duplicate".
- **Suggested fix:** Make the event insert the very first durable step after signature verification (one insert path for all outcomes), then branch on lookup/amount/transition and update `processing_status`. Ordering becomes: verify -> insert-or-duplicate -> classify -> apply -> mark.

## Finding 5: Idempotency "store the 502/409 as a completed response" is unreachable with the chosen wiring — error bodies are rendered by `@RestControllerAdvice` after the controller has already lost control
- **Severity:** High
- **Location:** Phase 6, "Architecture" — `phase-06-idempotency.md:31`, `:35`, `:41`; Phase 3 `phase-03-provider-interface-and-mock-provider.md:43`, `:53`; Phase 1 `phase-01-project-skeleton.md:35`
- **Flaw:** P6:31 chooses explicit `begin/complete/abandon` calls in `PaymentController`. P3:53 propagates provider failure as `ProviderException` mapped to 502 by `ProblemDetailsHandler` (P3:43, a `@RestControllerAdvice`, P1:35). P6:35 requires that 502 to be *stored* and replayed. The controller never sees the RFC 7807 body or status the advice produces; by the time the advice runs, the controller frame is gone. Likewise `OrderAlreadyExistsException` (P6:41), `UnknownProviderException` 400 (P3:32), and the 409 illegal-transition path are all exceptions, and the plan never says which of them are "completed" vs "abandon". P6:49 "abandon() in a finally-on-exception path" would, read literally, abandon the 502 too — directly contradicting P6:35.
- **Failure scenario:** Provider down. Request with K1 -> orchestrator throws `ProviderException` -> controller's exception path runs `abandon(K1)` -> advice renders 502. Merchant retries K1 -> `begin()` NEW -> second CREATED row? No — V7 409 (Finding 1), but even without V7: second provider call, second FAILED row, the "replay must not call the provider" criterion (P6:60) is violated. Alternatively, if the implementer catches `ProviderException` in the controller to store it, they must hand-build the problem detail, duplicating `ProblemDetailsHandler`.
- **Evidence:** P6:35 "Provider failure (502) is a *completed* response and is stored"; P6:49 "`abandon()` in a finally-on-exception path"; P3:43 "`common/ProblemDetailsHandler` (502, 400 mappings)".
- **Suggested fix:** Either (a) move idempotency to a `OncePerRequestFilter`/`HandlerInterceptor` that wraps the response (`ContentCachingResponseWrapper`) and stores status+body in `afterCompletion` for *all* outcomes, with an explicit allow-list of stored statuses (201, 409, 422, 502) and abandon only on 5xx-from-unexpected; or (b) keep controller calls but have the orchestrator return a result type (`Created | ProviderFailed | OrderExists`) instead of throwing, and have the controller build the `ProblemDetail` through a shared factory used by the advice. Write the completed-vs-abandoned table into the phase.

## Finding 6: A key stuck IN_PROGRESS after a crash locks the merchant out for 24 h with no recovery path
- **Severity:** Medium
- **Location:** Phase 6, "Requirements" + "Architecture" — `phase-06-idempotency.md:20`, `:21`, `:33`, `:51`
- **Flaw:** `begin()` commits IN_PROGRESS in its own `REQUIRES_NEW` tx (P6:33) before the real work. The only exits are `complete()` and `abandon()` on a caught exception. JVM kill, container OOM, `docker compose restart gateway` mid-request, or a thread death leave the row IN_PROGRESS until the 24 h TTL sweeper (P6:21/51). There is no staleness bound on IN_PROGRESS.
- **Failure scenario:** Merchant sends K1; gateway dies between tx1 and tx2 (the exact case P3:64 calls "acceptable"). Merchant retries K1 every 30 s as real integrations do -> 409 `IDEMPOTENCY_IN_PROGRESS` for 24 h. Switching to K2 hits Finding 1/2 (CREATED row + V7 -> 409). Net: the order is unrecoverable by the merchant in increment 1, and `docker compose restart` during the Postman run reproduces it.
- **Evidence:** P6:20 "Same key while first request still in progress -> 409"; P6:21 "Keys expire after 24h"; no mention of an IN_PROGRESS lease/timeout anywhere in P6.
- **Suggested fix:** Store `in_progress_since`; in `begin()`, treat IN_PROGRESS older than e.g. 60 s (> provider timeouts 2 s + 5 s, P3:20) as abandoned: `UPDATE ... SET status='IN_PROGRESS', in_progress_since=now() WHERE ... AND status='IN_PROGRESS' AND in_progress_since < now()-interval` and take ownership if 1 row updated. Teach it as "lease, not lock" — a natural bridge to increment 2.

## Finding 7: `MerchantAuthFilter` 401s and crypto failures cannot reach `ProblemDetailsHandler`; V5 Java migration needs `FLUXPAY_SECRET_KEY` in every test context or `./mvnw verify` fails to load
- **Severity:** High
- **Location:** Phase 5, "Requirements" + "Architecture" — `phase-05-merchant-hmac-auth.md:18`, `:21`, `:29`, `:33`, `:35`, `:38`, `:39`; Phase 1 `phase-01-project-skeleton.md:35`
- **Flaw:** (a) P5:29 is an `OncePerRequestFilter`; `@RestControllerAdvice` (P1:35) only handles exceptions thrown from handler methods. Nothing in P5 says how the five 401 problem-detail bodies (P5:18) are written from the filter, nor what happens when `SecretCipher.decrypt` throws (`AEADBadTagException` on key mismatch, bad base64 key at startup). An unhandled filter exception becomes a Tomcat 500 HTML page with a stack trace — a trust-boundary leak on the auth path. (b) P5:21/35/38 run a Flyway *Java* migration that encrypts with the env key at migration time. Every Testcontainers context (P1:48, all ITs from phase 5 on) and every `docker compose up` must have the key, but P5:39 only lists `docker-compose.yml` and `.env.example`; no test profile/property is mentioned. (c) The key used at V5 time is baked into the DB volume; running the gateway later with a different key (README `openssl rand` vs `.env.example` dev key, P5:39/63) makes every DEMO request fail with an undefined error, and the migration cannot be re-run because Flyway already applied V5.
- **Failure scenario:** Dev runs `docker compose up` with `.env.example` key -> V5 encrypts with K_dev. Later follows README and generates a fresh key into `.env` -> gateway boots fine (no startup check) -> first signed request -> `decrypt` throws -> filter 500 with stack trace -> Postman collection "works end to end" (P5:58) silently stops working with no `AUTH_*` code to point at. Separately, `./mvnw verify` on a clean checkout without the key: context fails in V5 for every IT -> `plan.md:62` acceptance red.
- **Evidence:** P5:33 "Fail closed. Log reason at WARN" — no response-writing mechanism named; P5:38 "`V5__EncryptMerchantSecrets.java` (Flyway `BaseJavaMigration`)"; P5:39 Modify list lacks any test configuration; P1:35 "`ProblemDetailsHandler` (`@RestControllerAdvice`...)".
- **Suggested fix:** Give the filter an injected `ProblemDetailWriter` (shared with the advice) that serialises RFC 7807 directly to the response; catch `GeneralSecurityException` in the filter -> 401 `AUTH_UNKNOWN_MERCHANT` or a new `AUTH_SECRET_UNREADABLE`, never 500. Add a startup self-check that decrypts the DEMO secret and fails fast with a clear message if the key is wrong. Add `FLUXPAY_SECRET_KEY` to `src/test/resources/application-test.yml` (or `@DynamicPropertySource` in `AbstractIntegrationTest`) and list it in P5 "Modify".

## Finding 8: Expiry sweeper is a single batch transaction with no poison-row handling, and it runs live inside the shared IT context while tests move the `Clock`
- **Severity:** Medium
- **Location:** Phase 2, "Requirements" + "Architecture" + steps — `phase-02-payment-state-machine.md:20`, `:31`, `:32`, `:54`; Phase 1 `phase-01-project-skeleton.md:35`, `:48`; Phase 4 `phase-04-sync-webhook-and-deduplication.md:47`
- **Flaw:** (a) `expireOverdue()` is one orchestrator method owning the tx (P2:31) over "PENDING with `expires_at < now`" (P2:20). If any single row fails (optimistic-lock from the deferred webhook race, a transition-row insert error), the whole batch rolls back and the same rows are retried every 30 s forever — one bad row blocks all expiries. (b) `@EnableScheduling` is on in the main profile (P2:52) and `AbstractIntegrationTest` is a cached `@SpringBootTest` context (P1:48). Tests manipulate the `Clock` bean for determinism (P1:35, P2:54). A test-controlled clock jumped forward by one IT makes the background sweeper, running on its own thread, expire PENDING payments that *another* IT in the same JVM just created.
- **Failure scenario:** `PaymentLifecycleIT` moves the clock +16 min to prove expiry; while it runs, `WebhookIngestionIT` (P4:47) creates a payment and posts a SUCCESS webhook; the scheduled sweeper fires between the two steps -> payment EXPIRED -> webhook REJECTED -> assertion "valid -> SUCCEEDED" fails intermittently. Classic order-dependent flake that only appears on CI.
- **Evidence:** P2:32 "`@Scheduled(fixedDelay=30s)` -> `orchestrator.expireOverdue()`"; P2:54 "sweeper expires an overdue payment (use the `Clock` bean)"; no `spring.task.scheduling` disable or test profile mentioned in P2:43.
- **Suggested fix:** Per-row transactions (`REQUIRES_NEW` per payment, catch and log per row, continue). Disable scheduling in the test profile (`@ConditionalOnProperty` on the sweeper, or `@EnableScheduling` on a config excluded in tests) and call `expireOverdue()` explicitly in ITs. Use a per-test fixed `Clock` only through the orchestrator (`MutableClock` reset in `@AfterEach`).

## Finding 9: Mock-provider `WebhookSender` retry/delay semantics are underspecified in ways that hang the pay endpoint or inflate the "exactly one DUPLICATE row" assertion
- **Severity:** Medium
- **Location:** Phase 4, "Requirements" + "Architecture" + steps — `phase-04-sync-webhook-and-deduplication.md:17`, `:31`, `:62`, `:66`; Phase 3 `phase-03-provider-interface-and-mock-provider.md:20`
- **Flaw:** P4:17 defines `delay-ms`, `duplicates`, `retry-on-non-200 (3, 1 s backoff)`, but not: whether the sender runs synchronously inside `POST /mock/pay/{providerRef}`, what the sender's HTTP timeouts are (only the gateway's are fixed at P3:20), whether a transport exception/timeout counts as "non-200" for retry, or whether `duplicates` are also retried. P4:62's exercise sets `delay-ms=70000`.
- **Failure scenario:** (1) Sync sender + 70 s delay -> the Postman "pay" request blocks 70 s (+ up to 3 s retries); with default compose/Tomcat settings this looks like a hang, and the P4:61 Postman folder cannot be run as a collection. (2) Sender timeout unset -> gateway stalls (e.g. Finding 3's rollback path) -> sender waits indefinitely; or if timeout is set and counted as retry, the first webhook *was* applied, each retry is a duplicate: `duplicates=1` yields 1 APPLIED + up to 4 DUPLICATE rows, breaking the P4:66 criterion "exactly one APPLIED and one DUPLICATE row". (3) `WebhookSenderTest` (P4:47) "duplicates and retry counts" cannot be written against undefined semantics, so it will be written to whatever the first implementation does — a phantom test.
- **Evidence:** P4:17 "`mock.callback.retry-on-non-200` (default 3, with 1s backoff)"; P4:31 "`webhook/WebhookSender` (RestClient, signing, delay, duplicates, retry)" — no timeout, no threading model; P4:66 "exactly one APPLIED and one DUPLICATE row".
- **Suggested fix:** Specify: sender is async (`@Async`/single-thread executor) so `/mock/pay` returns 202 immediately; sender RestClient connect 2 s / read 5 s; retry on non-2xx *and* on transport error, max 3, with `eventId` unchanged across retries and duplicates; test asserts on *attempt count per eventId* rather than DB row counts in the gateway. Relax P4:66 to "exactly one APPLIED row; all others DUPLICATE; exactly one transition row".
