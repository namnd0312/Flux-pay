## Finding 1: Merchant identity contract drifts across brainstorm, phase 1, phase 2 and phase 5 (three identifiers, two header schemes, two Postman env names)
- **Severity:** High
- **Location:** Phase 5 "Requirements" — `phase-05-merchant-hmac-auth.md:17`; Phase 2 "Overview" — `phase-02-payment-state-machine.md:13`; Phase 1 "Architecture" — `phase-01-project-skeleton.md:33,49`; Phase 5 step 7 — `phase-05-merchant-hmac-auth.md:49`; `brainstorm:41,66`
- **Flaw:** The user decided the API-key header is `X-Merchant-Id` (`brainstorm:41` "API key (`X-Merchant-Id`)", `brainstorm:66` request headers `X-Merchant-Id, X-Timestamp, X-Signature, Idempotency-Key`). The plan silently renames it to `X-Api-Key` (`phase-05:17`) and turns `X-Merchant-Id` into a throwaway "trusted" header that phase 2 introduces (`phase-02:13`) and phase 5 deletes (`phase-05:39,48`). To support this, `merchants` grows three identifiers: `id uuid`, `code varchar unique`, `api_key varchar unique` (`phase-01:33`); `code` is never referenced again in any phase. Postman env vars also diverge: phase 1 declares `merchantId, merchantSecret` (`phase-01:49`), phase 5 uses `merchantApiKey, merchantSecret` (`phase-05:49`).
- **Failure scenario:** Postman collection built in phase 1-4 against `X-Merchant-Id` + `{{merchantId}}` breaks in phase 5; the learner rewrites requests instead of adding two headers. Learning note 04 explains an `X-Api-Key` header that contradicts the brainstorm the learner approved. `merchants.code` ships as a dead column.
- **Evidence:** `phase-05:13` "Replace the trusted `X-Merchant-Id` header with ... API key"; `phase-05:17` "`X-Api-Key`, `X-Timestamp`, `X-Signature`"; `brainstorm:41` "API key (`X-Merchant-Id`)".
- **Suggested fix:** One header name for the whole increment, matching the decision: `X-Merchant-Id` carries the api key from phase 2 onward (unverified until phase 5). Phase 5 then only *adds* `X-Timestamp` + `X-Signature`; nothing is deleted, Postman env stays `merchantId`. Drop `merchants.code`; `api_key` is the public identifier, `id` the PK. Gained: zero throwaway header code, note matches decision. Lost: nothing.

## Finding 2: Unique `(merchant_id, order_id)` + "502 is a completed, replayed response" makes every failed/expired/cancelled order un-retriable forever
- **Severity:** High
- **Location:** Phase 6 "Architecture" — `phase-06-idempotency.md:35`; Phase 6 "Requirements" — `phase-06-idempotency.md:22`; Phase 6 step 6 — `phase-06-idempotency.md:50`; Phase 3 "Requirements" — `phase-03-provider-interface-and-mock-provider.md:19`
- **Flaw:** Phase 3 transitions the payment to FAILED and returns 502 when the provider is down (`phase-03:19`). Phase 6 says that 502 is stored and replayed for the same key and "the merchant must use a new key for a new attempt" (`phase-06:35`). But a new key with the same `orderId` hits V7 `unique (merchant_id, order_id)` and returns `409 ORDER_ALREADY_EXISTS` (`phase-06:22,50`). Same for EXPIRED and CANCELLED payments (customer abandons, comes back, retries the same order). The two guards the note is supposed to reconcile ("explains why both exist", `phase-06:13`) actually contradict each other on the most common real-gateway flow (VNPAY `vnp_TxnRef` is the merchant order id and is retried after failure).
- **Failure scenario:** Postman step 10 "new key same orderId (409)" passes, and the learner is taught that a gateway must reject re-attempts of a failed order. The failure-demo flow in phase 3 ("stop mock-provider -> 502 and payment FAILED", `phase-03:55`) followed by "start mock-provider, try again" returns 409 forever for `ORD-1`.
- **Evidence:** `phase-06:35` "retrying with the same key replays 502; the merchant must use a new key for a new attempt"; `phase-06:22` "Duplicate `orderId` for the same merchant with a different key -> 409 `ORDER_ALREADY_EXISTS`"; no partial-index or status condition anywhere in V7 description (`phase-06:37,50`).
- **Suggested fix:** Keep the decided second guard but make it a partial unique index: `UNIQUE (merchant_id, order_id) WHERE status IN ('CREATED','PENDING','SUCCEEDED')`. Update `phase-06:22` to "while a non-failed payment exists for that order", and add one IT case: FAILED order can be re-created with a new key. Alternative (simpler, bigger scope change vs brainstorm:82): drop V7 entirely and let the idempotency key be the only guard, explaining in the note why order-level uniqueness is business policy, not gateway policy. Needs the user's call since `brainstorm:82` names the second guard.

## Finding 3: Encrypted-at-rest merchant secrets via a Flyway Java migration is gold plating; its stated rationale is false and the file name is inconsistent within the phase
- **Severity:** High
- **Location:** Phase 5 "Requirements" — `phase-05-merchant-hmac-auth.md:21`; Phase 5 "Architecture" — `phase-05-merchant-hmac-auth.md:35`; Phase 5 "Related Code Files" — `phase-05-merchant-hmac-auth.md:38`; Phase 5 "Risk Assessment" — `phase-05-merchant-hmac-auth.md:61-63`
- **Flaw:** For one seeded demo merchant, the plan adds `SecretCipher` (AES-GCM), `SecretCipherTest`, a `BaseJavaMigration` that must obtain a key at Flyway time (before the Spring context exists), `FLUXPAY_SECRET_KEY` plumbing in compose/README/`.env.example`, and a key-loss risk. None of the stated learning goals (`brainstorm:12`) is "secret storage"; the note itself concedes the mechanism "is still not production grade (KMS/HSM)" (`phase-05:44`). The justification for choosing the Java migration — "so the key never appears in SQL" (`phase-05:35`) — is wrong: a SQL `UPDATE` with a precomputed *ciphertext* does not expose the key, and the dev key is committed in `.env.example` anyway (`phase-05:63`). The phase also names the migration two ways: `V5__encrypt_merchant_secrets.sql` (`phase-05:35`) vs `V5__EncryptMerchantSecrets.java` (`phase-05:38`), with the decision text waffling across three options in one sentence.
- **Failure scenario:** The learner spends a large share of the 1-day phase on Flyway Java-migration classpath/ordering quirks and AES-GCM IV handling instead of on the HMAC lesson (replay window, body signing). A migration that depends on an env var is non-reproducible: run once with key A, the row is permanently bound to A; a fresh teammate with key B gets `AUTH_BAD_SIGNATURE` on every request with no obvious cause.
- **Evidence:** `phase-05:35` "simplest = `V5` deletes and re-inserts DEMO ...; alternative: Flyway Java migration ... Choose the Java migration so the key never appears in SQL."; `brainstorm:85` "Merchant secret encrypted at rest with local key" (approved design, not a section-4 decision).
- **Suggested fix:** Present to the user as a trade-off, since `brainstorm:85` is approved design. Option A (cut): keep `secret` plaintext in increment 1, one paragraph in note 04 on KMS/at-rest encryption, remove `SecretCipher`, V5, key env, `.env.example`. Option B (keep, simplify): `V5__encrypt_merchant_secret.sql` with a precomputed ciphertext for the committed dev key, generated once by `SecretCipherTest`; no Java migration. Either way delete the inconsistent `.sql`/`.java` naming.

## Finding 4: `PaymentProvider` interface ships two methods for later phases and one for increment 4
- **Severity:** Medium
- **Location:** Phase 3 "Architecture" — `phase-03-provider-interface-and-mock-provider.md:28-31`; Phase 3 step 3 — `phase-03-provider-interface-and-mock-provider.md:49`
- **Flaw:** `queryStatus(...)` is declared "increment 4, throws UnsupportedOperationException for now" (`phase-03:30`) with its own `ProviderPaymentStatus` record (`phase-03:31`). `verifyWebhookSignature` / `parseWebhook` are declared in phase 3 and implemented in phase 4 (`phase-03:49`), so `MockProviderAdapter` must carry stub bodies for one phase. The phase's own success criterion is "adding a provider = one new class + config" (`phase-03:20`); the lesson of Strategy is that the interface is the contract *you need now*, not a forecast.
- **Failure scenario:** The phase 3 exercise `FakeBankAdapter` (`phase-03:56`) forces the learner to implement 5 methods, 3 of which throw. Note 02 has to explain methods that do nothing. `UnsupportedOperationException` stubs are the pattern the project should be teaching against.
- **Evidence:** `phase-03:30` "`queryStatus(String providerRef)` // increment 4, throws UnsupportedOperationException for now"; `phase-03:49` "Keep webhook methods in the interface now (so the contract is complete)".
- **Suggested fix:** Phase 3 interface = `code()` + `createPayment()` only. Phase 4 adds the two webhook methods (that *is* the phase-4 lesson: the adapter grows with the provider contract). `queryStatus` and `ProviderPaymentStatus` move to the increment-4 plan.

## Finding 5: Expiry sweeper is increment-4 scope pulled into phase 2, and its stated justification is void
- **Severity:** Medium
- **Location:** Phase 2 "Overview" — `phase-02-payment-state-machine.md:13,20,32`; Phase 2 step 1 — `phase-02-payment-state-machine.md:47`; Phase 2 "Risk Assessment" — `phase-02-payment-state-machine.md:64`; `brainstorm:114`
- **Flaw:** The brainstorm places "expiry sweeper" in increment 4 (`brainstorm:114`). Phase 2 justifies pulling it forward as "so EXPIRED is reachable for the failure demo" (`phase-02:13`), but the same step already creates a temporary `PATCH /api/v1/payments/{id}/status` (`phase-02:47`) that can set EXPIRED directly. The sweeper then becomes a dependency for phase 4's exercise (`phase-04:62`) and phase 6's TTL job (`phase-06:21,51`), and it introduces the sweeper-vs-webhook race the plan immediately disclaims (`phase-02:64`). Cost: `@EnableScheduling`, `@Scheduled`, `Clock`-driven timing tests, 30 s + 1 min waits inside a Postman demo.
- **Failure scenario:** Phase 2 demo step 1 takes up to 90 s of wall-clock waiting per attempt; ITs for the sweeper need the `Clock` bean *and* scheduler control, which is the kind of test flakiness that erodes trust in `./mvnw verify` for a learner. The CREATED/PENDING-vs-sweeper race becomes an "acknowledged known bug" from phase 2 through the end of the increment.
- **Evidence:** `phase-02:13` "Minimal expiry sweeper so EXPIRED is reachable for the failure demo"; `phase-02:47` "call a temporary `PATCH /api/v1/payments/{id}/status`".
- **Suggested fix:** Evaluate expiry at transition time instead of by polling: in `PaymentStateMachine.transition()` (or the orchestrator), if `status == PENDING && expiresAt < clock.now()` treat the current state as EXPIRED (append the EXPIRED transition, then reject the incoming one). No scheduler, no race, deterministic tests via `Clock`. Keep the 30 s sweeper in increment 4 where the brainstorm put it. If the planner keeps the sweeper, say so explicitly as a deliberate move from increment 4 and drop the "needed for the demo" rationale.

## Finding 6: `REQUIRES_NEW` on `begin()` is inert where it is called, and the phase-6 exercise built on it has an unknown outcome
- **Severity:** Medium
- **Location:** Phase 6 "Architecture" — `phase-06-idempotency.md:31,33`; Phase 6 step 11 — `phase-06-idempotency.md:55`; Phase 6 "Risk Assessment" — `phase-06-idempotency.md:65`
- **Flaw:** The plan prefers "explicit calls in the controller" over AOP (`phase-06:31`) and then puts `begin()` in `REQUIRES_NEW` (`phase-06:33`). A controller method is not transactional, so there is no outer transaction to suspend; `REQUIRES_NEW` behaves exactly like `REQUIRED`. The "second DB connection per request, pool >= 2x concurrency" risk (`phase-06:65`) is therefore self-inflicted and false. The closing exercise "remove the `REQUIRES_NEW` ... explain why the row count changes (or why it does not, depending on isolation)" (`phase-06:55`) admits the planner does not know the result; in this wiring the count will not change, so the exercise teaches nothing and ends the increment on a non-event.
- **Failure scenario:** Learner removes the annotation, reruns the burst, sees 1 row either way, and concludes transaction propagation is irrelevant — the opposite of the increment-2 bridge the plan wants.
- **Evidence:** `phase-06:33` "`begin()` runs in its own transaction (`REQUIRES_NEW`)"; `phase-06:55` "explain why the row count changes (or why it does not, depending on isolation)".
- **Suggested fix:** Plain `@Transactional` on `begin()`/`complete()`/`abandon()`; delete the pool-size risk line. Replace the exercise with one whose outcome is known: swap `INSERT ... ON CONFLICT DO NOTHING` for `existsBy... then save` and rerun the burst — duplicate rows appear, proving the PK, not Java, is the arbiter (`phase-06:33` already states this thesis).

## Finding 7: Three overlapping burst mechanisms for one failure demo, with a hedged fallback inside the plan
- **Severity:** Medium
- **Location:** Phase 6 "Related Code Files" — `phase-06-idempotency.md:40,42`; Phase 6 "Risk Assessment" — `phase-06-idempotency.md:66`; `brainstorm:40`
- **Flaw:** Phase 6 creates `scripts/burst-create.sh` (`xargs -P 20`), a hand-rolled `scripts/sign.sh` with `openssl dgst -hmac` that must reproduce the exact `timestamp + "." + rawBody` HMAC contract from phase 5, *and* `ConcurrentCreateIT` with 50 threads (`phase-06:40,42`). The risk section already says "if too fiddly, fall back to a JUnit-driven burst only" (`phase-06:66`). The user chose JMeter as the load tool (`brainstorm:40`) and is already familiar with it (`brainstorm:30`); a 50-thread `.jmx` with a JSR223 HMAC pre-processor is the decided tool for exactly this.
- **Failure scenario:** `sign.sh` and the Postman CryptoJS script and `HmacSigner` become three implementations of the signing contract; one drifts (e.g. millis vs seconds timestamp) and the burst returns 50 x 401 instead of the intended demo, burning the session on shell debugging.
- **Evidence:** `phase-06:40` "`scripts/burst-create.sh` ... simplest: a `scripts/sign.sh` using `openssl dgst -sha256 -hmac`"; `phase-06:66` "if too fiddly, fall back to a JUnit-driven burst only".
- **Suggested fix:** Cut both shell scripts. Failure demo = run `ConcurrentCreateIT` against the phase-5 build with the assertion inverted/printed (50 rows), record the number in the note, then make it pass. If a visible out-of-process demo is wanted, add a single `load-tests/burst-create.jmx` (the decided tool, also seeds increment 2's `load-tests/` directory per `brainstorm:58`).

## Finding 8: Provider test-double strategy is undecided and the indecision is repeated in three phases
- **Severity:** Medium
- **Location:** Phase 3 "Related Code Files" — `phase-03-provider-interface-and-mock-provider.md:44`; Phase 6 "Related Code Files" — `phase-06-idempotency.md:42`; Phase 4 "Related Code Files" — `phase-04-sync-webhook-and-deduplication.md:47`; Phase 3 "Risk Assessment" — `phase-03-provider-interface-and-mock-provider.md:65`
- **Flaw:** Phase 3 says the IT stubs mock-provider "via `MockRestServiceServer` or WireMock-free approach" (`phase-03:44`); phase 6 says provider calls are counted "via `MockRestServiceServer` expect-once or a counting stub" (`phase-06:42`); phase 3 also flags that `@RestClientTest` artifact names in Boot 4 are unverified (`phase-03:65`). Phase 4's `WebhookIngestionIT` (`phase-04:47`) needs a PENDING payment with a `providerRef`, i.e. the same double, but says nothing. `mock-provider` is a separate Maven module, so gateway ITs cannot start it; `MockRestServiceServer` inside `@SpringBootTest` requires binding to the specific `RestClient.Builder`, which is fiddly and unrelated to any learning goal.
- **Failure scenario:** Each phase re-solves provider stubbing differently; by phase 6 there are two or three ways to fake the provider in the test tree, and the "1 provider call" assertion (`phase-06:59`) depends on whichever one was picked.
- **Evidence:** `phase-03:44` "stubbed via `MockRestServiceServer` or WireMock-free approach"; `phase-06:42` "`MockRestServiceServer` expect-once or a counting stub".
- **Suggested fix:** Decide once in phase 3: a `@TestConfiguration` `CountingFakeProvider implements PaymentProvider` (`code()="MOCK"`, records calls, can be told to throw `ProviderException`) registered `@Primary` in `AbstractIntegrationTest`. It exercises the very seam phase 3 teaches, needs no HTTP test tooling, and gives phase 6 its call counter for free. Keep `MockRestServiceServer` only for the single `MockProviderAdapterTest` unit test.

## Finding 9: Contract hygiene — speculative columns and inconsistent mock-provider paths/config prefixes
- **Severity:** Medium
- **Location:** Phase 1 "Architecture" — `phase-01-project-skeleton.md:33`; Phase 2 "Architecture" — `phase-02-payment-state-machine.md:28`; Phase 4 "Architecture" — `phase-04-sync-webhook-and-deduplication.md:27,36`; Phase 4 "Requirements" — `phase-04-sync-webhook-and-deduplication.md:17,33`; Phase 3 "Requirements" — `phase-03-provider-interface-and-mock-provider.md:17,52`
- **Flaw:**
  - `webhook_events.signature_valid` (`phase-04:27`) can only ever be `true`: invalid signatures return 401 *outside* the transaction and are never stored (`phase-04:36`). Dead column.
  - `payments.currency = VND` (`phase-02:28`) while multi-currency is explicitly deferred (`brainstorm:122`) and amount is "long VND" (`brainstorm:85`). Dead column.
  - `merchants.code` (`phase-01:33`) never referenced after seeding (see Finding 1).
  - mock-provider config uses three prefixes for one app: `mock.webhook.url`, `mock.callback.delay-ms` / `duplicates` / `retry-on-non-200`, `mock.secret` (`phase-04:17,33`), while the gateway side is uniformly `fluxpay.providers.mock.*` (`phase-03:34`, `phase-04:33`).
  - mock-provider routes: `/mock/v1/payments`, `/mock/v1/payments/{providerRef}` (`phase-03:17`) vs `/mock/pay/{providerRef}` without `v1` (`phase-03:52`, `phase-04:17`).
- **Failure scenario:** Columns that never change value get copied into increment 2-4 migrations and notes as if meaningful; the learner asks "when does `signature_valid` become false?" and there is no answer. Config-prefix drift produces the classic "property set but not read" hour of debugging in compose.
- **Evidence:** `phase-04:36` "verify signature (outside tx) -> 401 if invalid" with no store step, vs `phase-04:27` "signatureValid"; `phase-04:17` "`${mock.webhook.url}/webhooks/MOCK`" and "`mock.callback.delay-ms`"; `phase-04:33` "`mock.secret`".
- **Suggested fix:** Drop `signature_valid`, `currency`, `merchants.code`. One prefix `mock.*` with `mock.gateway-webhook-url`, `mock.secret`, `mock.callback.*`. One route prefix `/mock/v1/...` for both session and pay endpoints (or `/mock/...` for both).

## Finding 10: Phase 4 is too large for "one session" and the retry/backoff simulator is the cuttable part
- **Severity:** Medium
- **Location:** Phase 4 frontmatter/"Requirements" — `phase-04-sync-webhook-and-deduplication.md:7,17`; Phase 4 step 1a — `phase-04-sync-webhook-and-deduplication.md:51`; Phase 4 "Related Code Files" — `phase-04-sync-webhook-and-deduplication.md:45-47`; `brainstorm:125`
- **Flaw:** The brainstorm's success metric is "each inc-1 step runnable + verifiable via Postman within one session" (`brainstorm:125`). Phase 4 is 1.5 days (`phase-04:7`) and touches: V4, entity, repo, service, raw-body controller, adapter verify+parse, mock `PayController`, `WebhookSender` with delay + duplicates + retry-on-non-200 + 1 s backoff (`phase-04:17`), a naive endpoint written then deleted, 3 failure demos, 7 test classes/cases across two apps, 5 Postman requests, compose wiring, note 03. The retry-with-backoff simulator exists only to make demo 1a show "4 errors instead of 1" (`phase-04:51`); `duplicates=1` alone already produces the second webhook -> 409 that proves the lesson. Out-of-order delivery (decided in `brainstorm:38`) is not in phase 4 at all, so the decision is only partially honoured while an undecided feature (retry) is added.
- **Failure scenario:** The learner finishes the gateway half, runs out of session before `WebhookSender` retry logic and `WebhookSenderTest`, and the phase stays half-done with the naive endpoint not yet removed (`phase-04:59`) — exactly the "temporary endpoint leaks into next phase" risk the plan flags elsewhere (`phase-02:65`).
- **Evidence:** `phase-04:17` "`mock.callback.retry-on-non-200` (default 3, with 1s backoff) to imitate VNPAY retry behaviour"; `phase-04:51` "mock-provider retries 3 times -> gateway logs 4 errors for one payment".
- **Suggested fix:** Cut `retry-on-non-200` + backoff and its `WebhookSenderTest` cases from increment 1; keep `delay-ms` and `duplicates` (both needed by demos and by the phase-4 exercise). Demo 1a becomes "duplicates=1 -> second webhook 409 -> a real provider would now retry, see note". Re-estimate at 1 day. Move retry simulation (and out-of-order) to the increment-2 plan where concurrent/duplicate webhooks are the subject.
