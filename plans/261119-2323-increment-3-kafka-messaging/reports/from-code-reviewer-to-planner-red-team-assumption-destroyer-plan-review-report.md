# Red-team plan review: Assumption Destroyer (Scope Auditor + Contract Verifier)

Plan: `plans/261119-2323-increment-3-kafka-messaging/`. Read-only review; nothing built or run. Paths relative to repo root. Claims about Kafka / Spring Kafka / Hibernate runtime behaviour come from knowledge, not from a run here; each is marked "verify by spike".

## Finding 1: `unique(payment_id)` notification insert inside `transition` turns the cancel-vs-webhook race into a deadlock or duplicate-key 500
- **Severity:** Critical
- **Location:** Phase 4, "Requirements" (first bullet) + "Architecture"; contradicts Phase 3 "Risk Assessment" (deadlock bullet)
- **Flaw:** Plan adds a third contended resource (unique index on `merchant_notifications.payment_id`) inside the payment transaction and never analyses its order against the payment row lock. Webhook path: row lock first (`findByIdForUpdate`), then notification insert. Cancel / sweeper: no row lock, insert executes first (JdbcClient runs immediately; Hibernate also orders inserts before updates), payment `UPDATE` only at flush/commit. Opposite order.
- **Failure scenario:** Cancel T1 and webhook T2 both read PENDING. (a) T1 inserts notification, T2 (holding the row lock) inserts and waits on T1's index entry, T1 commits -> `UPDATE payments` waits on T2's row lock -> deadlock, Postgres aborts one after `deadlock_timeout`. (b) T2 inserts first and commits, T1's insert gets unique violation. In both cases the cancel loser gets `CannotAcquireLockException` / `DuplicateKeyException`, not `OptimisticLockingFailureException`, so `OptimisticRetry` does not retry and the merchant gets 500. `on conflict do nothing` does not help: it also waits for the in-flight conflicting row.
- **Evidence:** Plan P4: "`unique(payment_id)` backs 'one terminal notification per payment'", "`MerchantNotificationStore` (JdbcClient)"; P3 risk: "Deadlock: only this path takes two locks ... cancel and sweeper take the payment only". Code: `gateway/src/main/java/com/fluxpay/gateway/payment/OptimisticRetry.java:57` (catches only `OptimisticLockingFailureException`); `payment/PaymentOrchestrator.java:149` (cancel, no lock), `:194` (sweeper); `webhook/WebhookPaymentApplier.java:97-99` (lock then transition); `common/ProblemDetailsHandler.java:104` (everything else -> 500, no `DataIntegrityViolation` handler). Consumers that break: `gateway/src/test/java/com/fluxpay/gateway/payment/WebhookVsCancelRaceIT.java:78,114` (200 races, counts server errors), `payment/OptimisticLockConflictIT.java:86,94` (two direct terminal transitions on one payment), `load-tests/webhook-vs-cancel.jmx:114` (cancel must be `200|409`).
- **Suggested fix:** Flush the payment `UPDATE` (version check + row lock) before the notification insert so every path takes payment row then index; or drop the unique constraint and rely on the terminal-state rule. Add the lock-order analysis to P4 risks and make `WebhookVsCancelRaceIT` an explicit P4 gate.

## Finding 2: Phase 2 "failure first" demo does not lose events with the described means
- **Severity:** High
- **Location:** Phase 2, "Implementation Steps" step 1; "Success Criteria" bullet 1
- **Flaw:** Assumes "pause broker -> POST -> resume -> rows stay RECEIVED". `KafkaTemplate.send` is asynchronous: with metadata already cached the record is buffered and delivered after resume while inside `delivery.timeout.ms` (default 120s). The ~5s producer timeouts that would make it fail fast are introduced only in step 2, after the demo. Verify by spike.
- **Failure scenario:** (a) Pause container 10s, POST N, resume: producer flushes the buffer, consumer applies, test asserting "payments stay PENDING" goes red, i.e. the naive path looks correct and the lesson is inverted. (b) Alternative "point the producer at a closed port": `spring.kafka.bootstrap-servers` is a context property, so this is a new Spring context; no metadata -> each `send` blocks the HTTP thread for `max.block.ms` (default 60s) then throws -> 500, not "assert all 200"; and "resume" is impossible because the port cannot be re-pointed. (c) Pausing the one static broker also freezes the in-context listener past its session timeout; a test failure before unpause leaves every later IT class hanging.
- **Evidence:** Plan P2 step 1: "pause the Kafka container (or point the producer at a closed port), POST N signed webhooks, assert all 200, resume, wait; assert ledger rows stay `RECEIVED`"; step 2: "`max.block.ms` and `delivery.timeout.ms` about 5s". Code: `gateway/src/main/resources/application.yml` has no `spring.kafka` block (all defaults at step 1); `gateway/src/test/java/com/fluxpay/gateway/AbstractIntegrationTest.java:50-54` (one static container per JVM, same pattern planned for Kafka, no per-class lifecycle).
- **Suggested fix:** Define the loss mechanism precisely: process death between commit and send (test: commit ledger row, discard the producer without flush / skip the send, show nothing ever republishes), or set short producer timeouts before the demo and hold the pause longer than `delivery.timeout.ms`. Unpause in `finally`. Drop the closed-port variant.

## Finding 3: Retry schedule runs on database `now()`; the test clock cannot move it, so cap/backoff tests need minutes of real waiting
- **Severity:** High
- **Location:** Phase 2, "Architecture" (relay SQL bullet) + steps 5-6; Phase 4 step 4; Phase 5 "Requirements" (settle time)
- **Flaw:** Every IT today controls time through `MutableClock`. The plan moves retry timing to DB `now()` and still promises "Awaitility, no sleeps" without saying how tests advance it.
- **Failure scenario:** Webhook cap test (`RETRY_EXHAUSTED` at 12 attempts, 1s doubling to 30s): waits 1+2+4+8+16+30x6 = 211s real time. Notification "always 500 -> `DEAD` after 6": 1+5+15+60+120 = 201s. "500 three times then 200": 21s. Each needs a `publishDue()` call after every due time because the scheduler is off. Either `verify` grows by ~7+ minutes, or the implementer back-dates `available_at` by SQL (unplanned fixture) or shortens backoff per class with `@TestPropertySource` (new Spring context per class, see Finding 5). Same number breaks the load harness: settle "must exceed the longest retry window" = 211s vs default 20s, per run.
- **Evidence:** Plan P2: "Relay SQL compares `available_at` with the database `now()`. Tests keep `fluxpay.scheduling.enabled=false` and call `publishDue()` directly"; research `researcher-02-...:45` same. Code: `gateway/src/test/java/com/fluxpay/gateway/MutableClock.java:14` ("without sleeping"), fixed at 2026-01-01 (`:19`); `application-test.yml` (`scheduling.enabled: false`); `load-tests/run.sh:12,76-77` (`QUIESCE_SECONDS` default 20).
- **Suggested fix:** Decide and write it down: backoff as configuration with a documented test helper that back-dates `available_at`, or compare against a bound parameter from the injected `Clock`. State the real settle seconds per scenario in P5.

- **Evidence:** `.gitignore:33` (`docker-compose.yml`), `:37` (`docker-compose.increment-1.yml`: the previous increment needed a hand-kept copy; plan has no equivalent step); `git tag` -> only `increment-1-done`; `load-tests/run.sh:16-17` (reset between runs), `:24` (one scenario per call, no matrix), `:46`, `:93-95`; `load-tests/verify-invariants.sql:9`; `README.md:127`; `docs/learning/09-load-test-and-bottlenecks.md:105` ("database xóa trước mỗi lượt"). - **Suggested fix:** P1 step 1: copy the compose file to `docker-compose.increment-2.yml` before touching it (and note `.env`). ## Finding 5: Shared-lifetime state makes several planned assertions and one test setup impossible
- **Severity:** High
- **Location:** Phase 1 "Architecture" (static container) + "Risk Assessment"; Phase 2 step 5 + "Success Criteria" bullet 2; Phase 4 step 5
- **Flaw:** Scope audit. Lifetimes: Postgres container = per JVM, never cleaned (no `truncate`/`delete from` anywhere in `gateway/src/test`); planned Kafka container = per JVM, shared; Spring contexts = at least 2 cached (default, plus `WebhookPessimisticLockIT` with its own property); consumer group ids fixed (`fluxpay-webhook-applier`, `fluxpay-merchant-notifier`) in every context; topics = broker-global. The plan treats each IT as if it owned the outbox, the topic and the group.
- **Failure scenario:** (1) After P4 every terminal transition in all 12 IT classes writes an outbox row nobody publishes (scheduler off). The first later `publishDue()` (batch 100) publishes other classes' rows first: "outbox unpublished = 0" and "order per key" in `OutboxRelayIT`/`BrokerOutageIT` become order-dependent. (2) "No ledger row without an outbox row ... = 0" is false in the shared DB: `EarlyWebhookIT` inserts ledger rows by raw SQL. (3) `SlowMerchantHeadOfLineIT` "run the topic with 1 partition in this test": the topic already exists with 3 partitions on the shared broker and partitions cannot be reduced; the property change also forks a third context. (4) Two contexts hold listeners in the same group on the same broker; whether the idle one is paused depends on spring-test's context pause mode, which the plan never mentions: paused -> rebalance on each context switch, not paused -> a record published by one class is applied by the other context's beans (different `MutableClock` instance, different `lock-timeout`). (5) Records still in flight when `@AfterEach` runs (`fake.reset()`, `clock.reset()`) are applied during the next test. (6) `MerchantNotificationIT` setting `callback_url` on the shared DEMO merchant leaks a dead `HttpServer` port into every later class's notifications.
- **Evidence:** `gateway/src/test/java/com/fluxpay/gateway/AbstractIntegrationTest.java:50-54`; `webhook/WebhookPessimisticLockIT.java:42` (`@TestPropertySource`); `webhook/EarlyWebhookIT.java:118` (raw ledger insert); 12 classes `extends AbstractIntegrationTest` (grep), including surefire-phase `ContextLoadsTest.java:19`; `ContextCache$PauseMode` present in the resolved `spring-test-7.0.9.jar`; plan grep for `truncate|cleanup|group-id|TestPropertySource|pause` in the phase files: 0 hits.
- **Suggested fix:** Scope every assertion to ids the test created. Give relay tests a way to publish only their own rows (or drain first). Per-context group id suffix or forbid new context-forking properties. Choose "pick payment ids that hash to one partition" for the head-of-line test and delete the 1-partition option. Fresh merchant per notification test. Add a P1 spike for context pause behaviour with a `@KafkaListener` in two contexts.

## Finding 6: Head-of-line demo and "the partition moves on" assume one thread per partition; default listener concurrency is 1
- **Severity:** High
- **Location:** Phase 4 "Key Insights" bullet 3 + step 5; Phase 3 "Key Insights" bullet 4; Phase 5 step 7 exercises
- **Flaw:** The plan never sets listener concurrency (grep: 0 hits for "concurrency" as a Kafka setting in any phase file). With Spring Kafka's default of one consumer thread per listener, that thread serves all 3 partitions in sequence. Verify by spike.
- **Failure scenario:** Slow merchant A on partition 0 delays merchant B on partition 2 exactly as much as on partition 0. The "force both onto one partition" work is unnecessary, the measured numbers do not show partition-level isolation, and note 13's claim "blocks its whole partition" plus the P5 exercise "`partitions=1` with a slow merchant" (expected to differ from 3) teach something the system does not do. Same for the 600ms blocking retry in P3: it stalls every partition of that listener.
- **Evidence:** Plan P4: "A slow merchant endpoint blocks its whole partition (head-of-line). Partitions are a coarse isolation tool"; P1 "Architecture" lists the full `spring.kafka` block without concurrency; `gateway/src/main/resources/application.yml` has no Kafka settings today.
- **Suggested fix:** Either set `spring.kafka.listener.concurrency` = partition count and say so (then the same-partition demo is meaningful and a different-partition control case should be added), or keep 1 and rewrite the lesson as "one thread, everything waits". Add the control case to `SlowMerchantHeadOfLineIT` either way.

## Finding 8: Single-transaction processor makes the pre-lock payment read share the persistence context; "webhook never loses a version check" stops being true
- **Severity:** Medium
- **Location:** Phase 3, "Architecture" bullet 1; "Risk Assessment" bullet 3
- **Flaw:** The claim is copied from a measurement of the current structure, where lookup reads run outside the transaction and the locking read gets a fresh entity. Inside one transaction the first read manages the entity; the later locking JPQL query takes the row lock but Hibernate returns the already-managed instance without refreshing its state. Verify by spike.
- **Failure scenario:** Cancel commits between the lookup and the lock. Processor holds stale PENDING/version, state machine allows the move, ledger is marked `APPLIED` by JdbcClient, the flush at commit fails the version check, everything rolls back. With `OptimisticRetry` removed this becomes a 1s reschedule round trip instead of an immediate `ILLEGAL_TRANSITION`; and the exception surfaces at commit, outside the callback, so the "retryable reason" catch must wrap `tx.execute`. The P5 prediction and note 09's "0 webhook retries" no longer describe this code.
- **Evidence:** Plan P3: "does not wrap its own `OptimisticRetry` loop ... with the row lock held the webhook path does not lose version checks, measured in note 09". Code: `gateway/src/main/java/com/fluxpay/gateway/webhook/WebhookPaymentApplier.java:74,81` (reads outside any transaction today), `:97-99` (fresh read inside); `payment/PaymentRepository.java` `findByIdForUpdate` (`@Lock` JPQL query, no refresh); `application.yml` `open-in-view: false`; `docs/learning/09-load-test-and-bottlenecks.md:99` (measurement of the old structure).
- **Suggested fix:** In the joined-transaction variant do the lookup as an id-only projection, or `refresh` after the lock; add a test: cancel commits between lookup and lock -> event `REJECTED ILLEGAL_TRANSITION` in the same attempt.
