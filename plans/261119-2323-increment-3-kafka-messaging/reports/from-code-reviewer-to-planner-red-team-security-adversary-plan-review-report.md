## Finding 1: The `NOTIFY=1` signature gate passes on an empty run (wrong merchant key in the SQL)
- **Severity:** High
- **Location:** Phase 4, section "Architecture" (last bullet); Phase 5, section "Requirements" (`run.sh` bullet)
- **Flaw:** Plan sets the callback URL with `update merchants set callback_url = ... where api_key = 'DEMO'`. No merchant has `api_key = 'DEMO'`. `DEMO` is the `name`; the api key is `demo-merchant`. The update matches 0 rows and psql reports success. Phase 5 gate is only "fail if `mock.merchant.bad_signature > 0`", with no "received > 0" check.
- **Failure scenario:** Learner and `run.sh` run the SQL as written -> 0 rows -> every notification goes `SKIPPED` (no callback URL) -> zero POSTs -> `bad_signature = 0` -> green. The planned HARD invariants also stay green: every terminal payment has a row, none is `PENDING`. A fully broken signer, or no delivery at all, is reported as PASSED in all `NOTIFY=1` runs and in note 14. Phase 5 itself says "a green invariant run can still be an empty run" but adds no non-empty guard for notifications.
- **Evidence:** `gateway/src/main/resources/db/migration/V2__seed_demo_merchant.sql:4-8` (`name 'DEMO'`, `api_key 'demo-merchant'`); `V5__encrypt_demo_merchant_secret.sql:10` (`WHERE api_key = 'demo-merchant'`); `load-tests/hmac-sign.groovy:69` (`'demo-merchant'`); phase-04:45; phase-05:29. Existing non-empty guard covers payments only: `load-tests/run.sh:92`.
- **Suggested fix:** Use `where api_key = 'demo-merchant'`; make `run.sh` assert the update touched exactly 1 row; with `NOTIFY=1` add HARD checks `mock.merchant.received delta > 0` and `notifications SKIPPED = 0`.

## Finding 2: "A signing regression fails tests" is false: no test in `./mvnw verify` verifies the callback signature independently
- **Severity:** High
- **Location:** Phase 4, section "Security Considerations" (3rd bullet); "Implementation Steps" 3-4
- **Flaw:** The only signature verifier is the fake merchant inside `mock-provider`, a separate module and process. The gateway ITs (step 4) use `com.sun.net.httpserver.HttpServer` and assert status, attempts, same `webhook-id`, different timestamps: no signature check listed. The signer unit test uses "a fixed vector" with no stated independent origin, so it can be produced by the code under test. No negative cases planned (tampered body, tampered timestamp, wrong secret, another merchant's secret).
- **Failure scenario:** Signer signs the re-serialized payload instead of the exact bytes sent, or omits the timestamp, or uses the wrong merchant's key. Unit test still matches its own vector; ITs pass (stub never verifies); `./mvnw verify` green. The only place it could surface is the manual compose lab or `NOTIFY=1`, which Finding 1 shows is vacuous. Repo already teaches the "bytes signed = bytes sent" trap (`gw/common/HmacSigner.java:12-13`, `load-tests/hmac-sign.groovy:7-11`) and then leaves it untested on the outbound side.
- **Evidence:** `gateway/pom.xml` dependency list (lines 21-92) has no `mock-provider` artifact; `mock-provider/pom.xml:20-40` likewise has no gateway artifact; phase-04:61 (step 4 assertions); phase-04:91 (claim). Existing signer exposes hex only (`gw/common/HmacSigner.java:20`), the mock has its own private hex HMAC (`mock-provider/src/main/java/com/fluxpay/mockprovider/webhook/WebhookSender.java:135-148`), so the base64 `v1,` format gets two fresh, unshared implementations.
- **Suggested fix:** In `MerchantNotificationIT` the stub must recompute HMAC over the raw request bytes with plain `javax.crypto` (not the gateway signer) and fail on mismatch. Signer test vector computed externally (`openssl dgst -sha256 -hmac ... -binary | base64`), command recorded in the test. Add negative tests: body, timestamp, id, secret each altered -> reject.

## Finding 3: Replay protection is claimed but never enforced: receiver has no timestamp tolerance, dedupe is in-memory only
- **Severity:** Medium
- **Location:** Phase 4, section "Architecture" (fake merchant bullet), "Security Considerations" (2nd bullet), README "callback contract" deliverable
- **Flaw:** Plan says the signature "covers id, timestamp and body, so a captured callback cannot be re-timestamped". That stops forging a new timestamp; it does nothing against replaying the capture unchanged. The fake merchant spec is "verifies the signature, remembers seen ids": no rejection of old `webhook-timestamp`, no knob for it, no test. Seen ids live in process memory, lost on restart. The check constraint also allows `http://`, so capture is trivial.
- **Failure scenario:** Attacker on the path captures one `payment.succeeded` callback. Replays it a day later or after a receiver restart: signature valid, id not in memory -> accepted as a fresh success event. Note 13 and the README contract present this receiver as the reference implementation a merchant copies. The project's own inbound side enforces the opposite standard (5 minute window).
- **Evidence:** phase-04:44, phase-04:90. Inbound standard: `gateway/src/main/resources/application.yml:41-42` (`timestamp-tolerance: 5m`), `gw/merchant/MerchantAuthFilter.java:120-123`. Research already states the rule and the plan dropped it: `research/researcher-02-...-report.md:171` ("rejects replays using `webhook-timestamp` within tolerance") and `:140` (Stripe tolerance 5 min).
- **Suggested fix:** Receiver rejects `|now - webhook-timestamp| > tolerance` (knob `MOCK_MERCHANT_TOLERANCE_S`, counter `mock.merchant.stale`); add a replay lab ("Tự phá thử": resend a captured request after the window); README contract states tolerance + id dedupe + constant-time compare as merchant obligations; note says `http://` is dev-only.

## Finding 4: SSRF mitigation is a prefix check plus a redirect claim that no step implements
- **Severity:** High
- **Location:** Phase 4, section "Security Considerations" (1st bullet); "Architecture" (`V10` bullet); "Implementation Steps" 4
- **Flaw:** (a) "Redirects are not followed" is asserted, but no step, config key or test implements it. Current HTTP client config sets timeouts only, and Spring Boot 4.1.2's JDK client follows redirects when the setting is unset. (b) The only destination control is a DB check "starts with `http://` or `https://`". No host/IP rule, no resolve-time check. (c) No `merchant.active` check on the send path. (d) "Operator-set by SQL only" is used to close the topic, while the plan lists the merchant self-service URL API as the known next step; the note would teach "scheme check = SSRF handled".
- **Failure scenario:** Gateway container sits on the compose network next to `db:5432`, `kafka:19092`, `mock-provider:8081` and its own unauthenticated management port. A callback URL (or a 302 from a real merchant host, followed by default) pointing at `http://localhost:9090/actuator/...`, `http://kafka:19092/` or `http://169.254.169.254/...` makes the gateway POST there; `last_status_code` / `last_error` then act as a port and response oracle (blind SSRF with feedback). Step 4's test list has 2xx, 500 x3, always-500, no URL, redelivered record: no 3xx case, so the default-follow behaviour ships unnoticed. Separately, a merchant deactivated (e.g. after secret compromise) keeps receiving signed payment data.
- **Evidence:** `gateway/src/main/resources/application.yml:4-8` (only `connect-timeout`, `read-timeout`; no `redirects`); `~/.m2/.../spring-boot-http-client-4.1.2.jar` `JdkHttpClientBuilder.asHttpClientRedirect`: null -> `HttpClient.Redirect.NORMAL` (bytecode inspected); no Apache/Jetty/Netty client in `gateway/pom.xml`, so the JDK client is used; `gw/provider/mock/MockProviderAdapter.java:47` shows the existing pattern `builder.clone()` inheriting global settings. Unauthenticated actuator: `load-tests/docker-compose.loadtest.yml:6-7,12-16`. Inactive check exists inbound only: `gw/merchant/MerchantAuthFilter.java:106-109`. Plan: phase-04:43, :61, :89; plan.md:43 (self-service API out of scope).
- **Suggested fix:** Dedicated `RestClient` for callbacks with redirects explicitly `DONT_FOLLOW` + an IT where the stub answers 302 to a second stub and the second stub must record zero hits. Deliverer skips inactive merchants (`SKIPPED_INACTIVE`). Note 13 gets an explicit SSRF section: what is NOT done (resolve-then-check private/loopback/link-local, DNS rebinding, port allow-list, egress proxy) and that these are prerequisites before any merchant-supplied URL. Add a "Tự phá thử": point the URL at `http://localhost:9090/actuator/health` and read `last_status_code`.

## Finding 5: Reusing the API signing secret for callbacks: the sign-off item hides the real cost (secret spreads to the mock-provider and to every callback verifier)
- **Severity:** Medium
- **Location:** Phase 4, section "Risk Assessment" (4th bullet), "Architecture" (`MOCK_MERCHANT_SECRET`), "Implementation Steps" 3
- **Flaw:** Plan frames the risk as "one secret, two formats" and mitigates only string confusion (step 3). That part holds: `id.timestamp.body` cannot equal the inbound canonical string. The actual exposure is not analysed: (a) whoever verifies callbacks must hold the secret that authorizes create/cancel; (b) `MOCK_MERCHANT_SECRET` puts the DEMO merchant's API secret into the mock-provider process, which today holds only the provider webhook secret and plays a different trust party; (c) one `secret` column, no key id in `v1,` -> no rotation story across a retry window; (d) the consumer now decrypts merchant secrets off the request path and the plan does not say what happens when decrypt fails.
- **Failure scenario:** Lesson teaches: give your webhook receiver the same secret as your API client. A leaked receiver config (commonly a less protected service) lets the holder sign `POST /api/v1/payments` and `.../cancel` as the merchant. On decrypt failure the notifier throws an unexpected exception -> 3 blocking attempts -> DLT, row stays `PENDING` forever, with no operator-visible state.
- **Evidence:** Single secret authorizes all API calls: `gw/merchant/MerchantAuthFilter.java:127,143`; schema `V1__create_merchants.sql:9` (one `secret` column). Mock-provider secrets today: `mock-provider/src/main/resources/application.yml:20` and `docker-compose.yml:50` (`MOCK_SECRET` only). Decrypt failure type exists and is handled only in the filter: `gw/merchant/MerchantAuthFilter.java:126-132`. Plan: phase-04:44, :60, :85.
- **Suggested fix:** This is a pending user decision; present it with the full trade-off. Option A (keep reuse): state (a)-(d) in note 13 as the cost, define decrypt-failure outcome (`DEAD` + reason token, ERROR log, no DLT). Option B (small, stricter): derive the callback key `HMAC(secret, "fluxpay-callback-v1")` in the signer, give the fake merchant only the derived value; ~10 lines, no schema change, and the receiver can no longer sign API requests.

## Finding 6: A hostile or merely slow merchant stalls notifications for all merchants; "partition-level isolation" is not what the plan builds
- **Severity:** Medium
- **Location:** plan.md "Known limits carried forward" (1st bullet); Phase 4 "Key Insights" (3rd), "Requirements" non-functional, step 5
- **Flaw:** Plan claims isolation is "partition-level". No phase sets listener concurrency, so the notifier group runs one consumer thread over all 3 partitions: head-of-line is global. No per-merchant budget, circuit, or attempt ceiling per time window. Terminal events are cheap for an authenticated merchant to mint: create + cancel.
- **Failure scenario:** Merchant A points its callback at an endpoint that accepts the connection and holds it. Each attempt costs up to connect 2s + read 5s of the only notifier thread; each payment gets 6 attempts = up to 42s of thread time. A loops create -> cancel 100 times (two signed API calls each, no rate limit until increment 4): about 70 minutes of notifier time during which merchant B's `payment.succeeded` callbacks queue behind A's. Step 5's "B is delivered within about one timeout" holds for one stalled record only, not for a backlog. Also unstated: whether the 5s read timeout bounds the whole exchange or only time to headers; `records x 7s` is the plan's safety argument for `max.poll.interval.ms` and is not proven by any test.
- **Evidence:** Cheap terminal transition: `gw/payment/PaymentOrchestrator.java:143-151` (cancel), `:125-131` (compensate), `:159-162` (sweeper) all go through `PaymentStateMachine.transition` (`gw/payment/PaymentStateMachine.java:49-58`). No request throttling anywhere: `gw/payment/dto/CreatePaymentRequest.java:13-18`, rate limit deferred (phase-05:81). No `concurrency` key in any phase file or in `gateway/src/main/resources/application.yml`. Plan: plan.md:53; phase-04:23, :32, :62.
- **Suggested fix:** State the truth in plan and note: with default concurrency isolation is none. Either set `concurrency = partitions` for the notifier and say so, or keep 1 and document it. Add a cheap per-merchant guard: skip-and-reschedule when a merchant has N consecutive failures (open for T seconds). Extend `SlowMerchantHeadOfLineIT` with a backlog case (20 stalled records for A, measure B) and a slow-drip body case; send with `toBodilessEntity()` and never read the merchant's body.

## Finding 7: The Kafka record is a second trust input (`fluxpay-outbox-id` header) on an unauthenticated broker; the plan's "trusts only the ledger row" covers the value only
- **Severity:** Medium
- **Location:** Phase 2, section "Security Considerations"; "Requirements" (reschedule bullet); Phase 1 "Security Considerations"; Phase 3 "Requirements"
- **Flaw:** Phase 2 says the consumer trusts nothing in the record beyond the id to look up. But the record also carries `fluxpay-outbox-id`, and the reschedule (`published_at = null`, `attempts + 1`) needs an outbox row id. Plan never says the consumer must derive that row from the database, or check that the header's row has the same topic and payload as the record. The broker is PLAINTEXT with no auth, reachable from every container and from `127.0.0.1:9092`.
- **Failure scenario:** Any local process produces a record to `fluxpay.webhook-events` with value = a real `RETRYABLE` ledger id and header = the outbox id of an unrelated row (for example a notification row). Consumer hits retry-later, runs `reschedule(headerId)`: an already published row from another topic is re-armed and republished, and its `attempts` advances toward `RETRY_EXHAUSTED` / `DEAD`. Notification rows in backoff get their attempts burned, so a merchant's callback dies early. Damage is bounded by consumer idempotency, but the cap introduced in this increment turns "extra deliveries" into "terminal give-up", which the lesson should not present as safe by construction.
- **Evidence:** Today no message path exists; all state changes are guarded by status predicates in SQL (`gw/webhook/WebhookEventStore.java:100-134`, `where id = :id and processing_status = 'RECEIVED'`), which is the pattern to keep. Plan: plan.md:34 (header), phase-02:31 (reschedule), phase-02:89 (conditional only on `published_at is not null`), phase-02:94-95 (claim), phase-01:72 (no auth).
- **Suggested fix:** Specify: header is for tracing only. `reschedule` selects the row by `(topic, payload = ledger/notification id)` with predicates `published_at is not null and attempts = :seen`, or validates header row topic + payload against the record before touching it. Add an IT: forged header pointing at another row -> no row changes. Say in note 11 that a record is untrusted input even from your own broker.

## Finding 8: Free-text error storage (`last_error varchar(200)`, DLT exception headers) breaks the repo's "stable token" rule and leaks or breaks on merchant-controlled content
- **Severity:** Medium
- **Location:** Phase 2 "Architecture" (`V9`); Phase 4 "Architecture" (`V10`), "Requirements" (`DEAD` ERROR log); Phase 3 "Security Considerations"
- **Flaw:** `outbox.last_error varchar(200)` and `merchant_notifications.last_error varchar(200)` hold exception text. Plan defines no truncation and no allow-list of codes. Phase 3 only says "keep parser errors free of payload content", while `DeadLetterPublishingRecoverer` publishes exception message and stack trace headers for every exception type, not just parser errors.
- **Failure scenario:** (1) Availability: HTTP client exception messages include the request URL and an excerpt of the response body, routinely over 200 chars. The "record result" transaction fails with value-too-long -> exception reaches the error handler -> 3 blocking attempts -> DLT; the row stays `PENDING` with a published outbox row and is never retried. A merchant triggers this at will by returning a 500 with a long body. (2) Exposure: a callback URL with credentials or a token in userinfo/query is copied into `last_error`, the ERROR log on `DEAD`, and DLT headers that lab (c) prints with `print.headers=true`; merchant-chosen response bytes land in logs and the database.
- **Evidence:** Repo convention is short fixed tokens, never free text: `V3__create_payments_and_transitions.sql:23-24,30` ("reason_code is a short stable token (never free text)"), `V4__create_webhook_events.sql:13` (`reject_reason VARCHAR(40)`), `gw/webhook/WebhookPaymentApplier.java:71,90,93,106` (fixed codes), `gw/provider/mock/MockProviderAdapter.java:25-26` ("the cause is logged, never returned"). Plan: phase-02:47, phase-04:43, phase-04:31, phase-03:80, phase-03:76 (already lists the stuck row as a limit without naming this trigger).
- **Suggested fix:** Store a reason token (`TIMEOUT`, `CONNECT_FAILED`, `HTTP_5XX`, `HTTP_3XX`, `HTTP_4XX`, `BROKER_SEND_FAILED`) plus `last_status_code`; no exception text in the database. If text is kept: truncate in the store method and strip URL userinfo/query. Never read the merchant's response body. Configure the recoverer to omit the stack-trace header (verify the option name in the Spring Kafka 4.1 reference during step 5) and add an IT asserting DLT headers contain no payload or URL.
